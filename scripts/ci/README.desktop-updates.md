# Desktop application updates

The desktop updater uses the official Tauri 2 plugin. It checks the configured
channel, downloads in the background, verifies the updater signature, then asks
the user before installation. Local operations drain and IndexedDB drafts must
finish saving before handing control to the system installer.

Settings live in the current OS user's Tauri configuration directory,
`updater-preferences.json`. They do not follow the SourceWeft account. Initial RC
installs select `preview`; stable installs select `stable`. Both default to
automatic checks and downloads. Installing a stable release does not change a
saved preview preference. Preview receives later stable releases and newer RCs.
All comparisons use SemVer. No downgrades or source fallback are permitted.

## Signing prerequisites

Create a protected GitHub environment named `desktop-release`. Set repository
variable `TAURI_UPDATER_PUBLIC_KEY` to the base64 public key generated by Tauri's
signer, and `WINDOWS_TIMESTAMP_URL` to the signing certificate provider's RFC 3161
timestamp service. The public key must be available to the release preflight as
well as protected build jobs, so use a repository variable.

Required protected secrets:

- `TAURI_SIGNING_PRIVATE_KEY` and, if encrypted, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`.
- `APPLE_CERTIFICATE` (base64 P12), `APPLE_CERTIFICATE_PASSWORD`,
  `APPLE_SIGNING_IDENTITY` (Developer ID Application identity), `APPLE_ID`,
  `APPLE_PASSWORD` (app-specific password), `APPLE_TEAM_ID`.
- `WINDOWS_CERTIFICATE` (base64 PFX) and `WINDOWS_CERTIFICATE_PASSWORD`.
- Existing `DOWNLOADS_S3_ACCESS_KEY_ID` and `DOWNLOADS_S3_SECRET_ACCESS_KEY` may
  remain repository secrets. Scope them to the download bucket only.

Keep the private updater key backed up outside GitHub. Do not generate it in each
release. This workflow expects an exportable Windows signing certificate; a
hardware/cloud signing service requires an explicitly designed integration,
never an unsigned fallback. Missing configuration fails the signed release.

See the official [updater](https://v2.tauri.app/plugin/updater/),
[macOS signing](https://v2.tauri.app/distribute/sign/macos/) and
[Windows signing](https://v2.tauri.app/distribute/sign/windows/) instructions for
credential provisioning. Updater signatures and platform code signing are
separate checks.

## Build and publish

PR package verification stays unsigned and has no production signing secrets.
The signed workflow builds these four explicit targets:

- `aarch64-apple-darwin`
- `x86_64-apple-darwin`
- `x86_64-pc-windows-msvc`
- `x86_64-unknown-linux-gnu` (Ubuntu 22.04 baseline, AppImage)

The generated Tauri release config enables updater artifacts and platform
signing. `build.rs` embeds the public key. Development binaries explicitly refuse
production update checks. Unsigned verification builds without a key report
`UPDATE_PUBLIC_KEY_NOT_CONFIGURED`; they cannot install updates.

macOS and Windows targets verify their OS distribution signatures (including macOS notarization). Linux verifies the x64 type-2 AppImage header and executable mode; it does not claim Apple/Windows code signing. Every target verifies its updater signature before producing an artifact description. The publication
job re-verifies updater signatures using Tauri's `minisign-verify` library, then
uploads immutable files and checks public SHA-256/size before promoting channels.
The 512 MiB limit is enforced on published files. The unmodified official plugin
buffers downloads; runtime size cancellation is best effort, not a hard memory
allocation guarantee. No partial-download persistence or resumable downloads.

Official clients use `https://download.sourceweft.com` with no storage prefix.
The update CLI rejects a different host/prefix; custom branded builds must define
their own compiled trust and publication configuration explicitly.

```text
releases/vVERSION/<target-qualified-installer>.dmg or .exe
releases/vVERSION/<target-qualified-update>.app.tar.gz or .exe
releases/vVERSION/<update>.sig
releases/vVERSION/updater.json
updates/stable.json
updates/preview.json
```

The immutable updater manifest retains its original control block. The channel
contains the same release content plus mutable `sourceweft` controls:

```json
{ "schemaVersion": 1, "distribution": "active", "revision": 1, "reason": "" }
```

`distribution` is `active`, `paused`, or `withdrawn`. It is enforced by SourceWeft's
Rust service, not by Tauri itself. Missing or invalid controls reject the update.
Each channel is a single complete JSON object written with ETag conditions;
there is no cross-channel transaction. Public channel caching must respect
`no-cache, max-age=0, must-revalidate`.

Stable releases update stable and initialize/advance preview unless preview is
already newer. Pre-releases only update preview. The website's `channels/*.json`
continues to be a distinct download-page protocol.

Completed target artifacts are reused on a workflow rerun, preserving signed
bytes. Never move an existing release tag or rebuild a published version. If an
artifact has expired or uploaded bytes differ, publish a new version. Publication
receipts record each successful channel operation; a partial failure is repaired
by rereading actual state and rerunning, without changing successful objects.

## Pause, resume, withdraw

Run the **Control desktop update distribution** workflow with an action, channel,
expected version and reason. `both` explicitly attempts both channels with that
version, recording each result; if their versions differ, control them separately.

- `pause`: prevent new downloads and installation; keep installed apps running.
- `resume`: explicitly allow the currently paused version again.
- `withdraw`: permanently reject this candidate. Publish a higher repair version,
  verify it, then explicitly resume its paused channel.

Publishing a new version into a paused/withdrawn channel preserves the pause.
Retries cannot undo it. In-flight downloads revalidate at 60-second intervals and
discard bytes on pause; installation always revalidates. Network/control failures
also stop installation. Static polling is not an instantaneous revocation system,
and cannot stop a system installer already launched. Pause does not remove public
installer URLs or GitHub assets. Configure CDN headers correctly; if existing CDN
rules override them, correct/purge those rules before relying on pause.

## First rollout and recovery

Existing clients lack the updater and require one manual installation. Deploy the
Web save-coordination UI before shipping the first updater-enabled client. A page
that cannot acknowledge saved drafts blocks installation with a clear error;
refresh/recover the page rather than bypassing the guard.

Validate two successive test versions on all four build targets before
promoting the stable channel. Check settings/login preservation, local work,
readonly DMG execution, permission denial, cancellation and network loss. Local
unit tests do not certify these installation paths.

No automatic binary/data rollback. Use a higher repair release or manual
installation if the app no longer starts. Do not rotate the public key in place:
retain the old-key channel for an old-key-signed bridge release which embeds a
new key and new channel URL; only then migrate users. Lost/compromised trust may
require manual installation.

## Verification

```sh
cargo build --locked --manifest-path scripts/ci/update-verifier/Cargo.toml
DESKTOP_UPDATE_VERIFIER=scripts/ci/update-verifier/target/debug/sourceweft-update-verifier node --test scripts/ci/desktop-update-signatures.test.mjs
node --test scripts/ci/desktop-update-manifest.test.mjs scripts/ci/publish-desktop-updates.test.mjs scripts/ci/publish-downloads.test.mjs
cargo test --locked --manifest-path apps/desktop/src-tauri/Cargo.toml
```

The signature integration test generates ephemeral test keys, never release keys.
No account/device telemetry is added. `updater.log` in the local configuration
directory records update status, versions, channel and safe error codes; it is
truncated once it exceeds 256 KiB. UI errors and CI receipts provide additional
diagnostics. Credentials, workfiles and chat content are never included.

## Linux packaging

Linux x64 is distributed as an AppImage, which is also the signed updater payload.
The verification and signed workflows use Ubuntu 22.04, install WebKitGTK 4.1,
GTK/AppIndicator and AppImage dependencies via `install-desktop-linux-deps.sh`,
and bundle GStreamer base/good support. AppImage is the only supported Linux
package format; Linux ARM64 and local device execution are not enabled.

Linux descriptors set `distributionSigned=false` and `notarized=false`: these
fields refer to OS code signing, not the mandatory `.AppImage.sig` updater
signature. Public signed publication requires all four build targets, including
Linux, before any update channel is promoted.

Users should place the AppImage in a writable folder, make it executable and run
it. Some systems require FUSE 2. The updater can replace a running AppImage; it
does not turn a standalone unpacked executable or a package-manager install into
an AppImage. Signed updates require the release public key to be embedded.

For an isolated build on a native Linux x64 host, build the toolchain image:

```sh
docker build --platform linux/amd64 -f scripts/ci/Dockerfile.desktop-linux -t sourceweft-desktop-linux-build:20260920 .
```

Copy the desktop sources and placeholder frontend into an isolated container's
`/work/apps/desktop` (omit `target`, `node_modules`, local environment files and
signing secrets), then run `tauri build --ci --no-sign --bundles appimage -- --locked`
there for an unsigned verification package. The image pins Node 24.18.0, Rust
1.94.1 and the same Tauri CLI version as the repository. Never promote that
verification artifact as a signed release.

The tested ARM Docker host cannot currently run the x64 toolchain:
Rust 1.94.1 crashes with SIGSEGV even for
`rustc --version`, before compiling project code. The Dockerfile checks compiler
startup explicitly. Use the native Ubuntu x64 CI runner to validate the package;
do not lower the Rust version or relabel an ARM package as x64.
